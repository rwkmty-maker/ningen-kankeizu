## 1. 概要

### 何をするアプリか
Excel の顧客表（知人管理表）を読み込み、一覧表示・あいまい検索・並べ替えを行い、行をダブルクリックすると「紹介者」「グループ」のつながりを関係図（HTML）にしてブラウザで開く、Windows 用の tkinter デスクトップアプリ。

- README の説明：「Excelファイルから顧客データを読み込み、検索・ソート・関係図の可視化を行うGUIアプリケーション」（README.md:3）
- ウィンドウ名：`Customer Nexus System - Hyper Edition Final v108`（customer_app.py:57, :39）。読み込み後は末尾に `［ファイルパス］` が付く（:315 `update_title_with_path`）
- 主な機能（コードで確認）
  1. Excel 読込（ボタン／ドラッグ＆ドロップ／起動時の引数／前回のファイルを自動で開く）
  2. 検索：部分一致＋AND/OR＋ひらがな→カタカナ＋ローマ字→カタカナ＋生年月日のゆれ＋「一文字違い」検索
  3. 行の文字色付け（Excel の A列の塗りつぶし色、または「出禁」等の文字から自動判定）
  4. 列見出しで並べ替え（自然順）・検索対象列の指定
  5. 関係図（networkx＋pyvis の部品で HTML を作り、Chrome のシークレット＋アプリモードで開く）
  6. フリガナ自動入力（Claude API で「本名」の読みを作り、Excel の「フリガナ」列に**直接書き込んで保存**する）

### 関係（誰と誰がどうつながるか）graph/graph_generator.py:110-152 `generate_customer_graph`
各行について、本人 u＝登録名 として：

| 条件 | 線の向き | つながり先のノード |
|---|---|---|
| 紹介者 ref があり、ref が名簿の登録名にある（自分以外） | ref → u | その人 |
| 紹介者 ref があるが名簿に無く、グループ grp が名簿の登録名にある | grp → u | その人 |

| 紹介者が空で、grp が名簿の登録名にある | grp → u | その人 |
| 紹介者が空で、grp が名簿に無い | grp → u | グループ名の箱（`GroupNode`） |
| 両方空 | 線なし | — |

- 紹介者は1人分しか扱わない（複数書いてあっても1つの文字として照合）。
- 実測（架空データ）：B の紹介者「架空A(友人)」→ `架空A→架空B` の線。A のグループ「G1」（登録名に無い）→ `G1→架空A`。D の紹介者「存在しない人」→ D は B の図に出ない。

### ふりがな列の扱い
- 検索で「フリガナ」列を特別に扱う処理は無い。全列検索（`search_index`）の一部として入るだけ（:920-925）。
- 半角カナ（例 ｻﾄｳ）は正規化（NFKC）で全角カナになる。入力のひらがなはカタカナにも直して探すので、**ひらがなで打ってもフリガナ列（カタカナ）に当たる**（実測：`たなか` → フリガナ `ﾀﾅｶ` の行がヒット）。
- フリガナ自動入力の書式：`既存のフリガナ(ｾｲﾒｲ)` のように括弧で追記（furigana_helper.py:66-90）。検索時は括弧が消えるので、両方の読みがつながった文字で照合される。

3. 「誕生日」ボタンから来た時は生年月日の昇順に並べ替え、他は今の並べ替え状態のまま表示（:1327-1335）
4. 表示（`update_list` :1439）。ここで**第一段階をもう一度計算し直して**、通常一致か一文字違いかを見分ける（:1460-1468）

絞り込み `run_search_filter`（:1340）は第一段階だけ（今の結果の中で）。

### 5-1. キーワードの分け方 `parse_search_keywords`（:1137-1184）
- OR：`｜` または `|`（前後の空白込み、連続も可）で分割（:1148）
- AND：半角・全角の空白で分割（:1154）
- 結果は［［AND語, AND語］, ［…］］の形（OR のリスト）
- **ローマ字の展開**：グループ内に英字（a-z, A-Z）を含む語があれば、それを `romaji_to_katakana` で変換したグループも OR で足す（:1160-1179）
- 実測例：
  - `田中 太郎` → [['田中','太郎']]、`田中｜山田` → [['田中'],['山田']]
  - `tanaka` → [['tanaka'],['タナカ']]、`yappu-` → [['yappu-'],['ヤップー']]、`田中 taro` → [['田中','taro'],['田中','タロ']]
  - **`OR` `AND` `&` は区切りとして扱わない**：`田中 OR 山田` → [['田中','OR','山田'],['田中','オr','山田']]（3語の AND になる）、`田中&山田` → [['田中&山田']]
  - ※ test_and_or_search.py / test_regression.py は `OR` `AND` `&` を区切りとして扱う**別の実装**をテストしている（§9）。本体とは食い違う。

### 5-2. 正規化 `normalize_text_unified`（utils/text_utils.py:23-34）
順番：①`str` 化 ②**NFKC**（全角英数→半角、半角カナ→全角カナ、ｶﾞ→ガ のように濁点も合成）③**大文字化** ④次の文字を削除：`−` `‐` `─` `━` `-` `(` `)` `.` `/` 空白（半角・全角）
- 実測：`０９０－１２３４－５６７８`→`09012345678`、`ﾀﾅｶ ﾀﾛｳ`→`タナカタロウ`、`(株)テスト`→`株テスト`、`Ａｂｃ`→`ABC`
- **しないこと**（実測）：`・` `_` `〜` `~` `ー` は残る。小さい字（ぁ）と大きい字（あ）、ヴとブ、旧字（渡邊と渡辺）は同じにしない。

### 5-3. ひらがな→カタカナ `hira_to_kata`（text_utils.py:7-20）
- U+3041〜U+3096 を +0x60 してカタカナにする。
- 検索語は「そのまま正規化」と「カタカナ化してから正規化」の2通りで探す（customer_app.py:1231-1232, :1246-1252）。
- **データ側はカタカナ化しない**ので、データがひらがなでキーワードがカタカナだと当たらない（コードから言えること）。

### 5-4. ローマ字→カタカナ `romaji_to_katakana`（text_utils.py:53-196）
- 小文字にしてから、表（長いもの順）を上から順に `str.replace` で文字列全体に当てていく方式（:188-192）。
- 実測：`tanaka`→タナカ、`kyouko`→キョウコ、`jun`→ジュン、`teru3`→テル3、`a-`→アー
- 実測で分かった変換のずれ：`kenichi`→ケニチ、`junichi`→ジュニチ、`shinichi`→シニチ、`tokyo`→トキョ、`abc123`→アbc123、`la`→ラ（表には `la`→ァ もあるが先に `la`→ラ が当たる）
- 単語の途中で区切りを間違えることがあるが、元の英字のグループも残るので、英字そのものでの検索は失われない。

### 5-5. 文字の部分一致 `get_single_keyword_mask`（:1221-1289）
- 検索対象列を指定していない：`search_index`（全列、ただし**生年月日の列は入らない**）に `str.contains`（正規表現なし）（:1249-1252）
- 検索対象列を指定している：その列だけをつないで正規化した文字に `str.contains`（:1239-1248）。**この時は生年月日列の表示文字（例 `H2(1990)/11/23`→`H219901123`）も文字として照合される**。
- AND：語ごとのマスクの積、OR：グループの和（:1206-1216）

### 5-6. 生年月日の検索（同じ関数の後半 :1254-1284）
- 実行条件：生年月日の隠し列があり、かつ（検索対象列の指定が無い、または指定に「生年月日」が入っている）（:1255-1259）
- 文字の一致と**OR**で足される（:1271, :1284）。数字を打つと、文字で当たった行＋誕生日が合う行の両方が出る。
- 手順：
  1. **区切りあり**として解析 `parse_date_with_separators`（utils/date_utils.py:268-338）。結果があればそれだけを使う（:1261-1271）
  2. 無ければ**区切りなし**として全パターンを出す `parse_fuzzy_date`（date_utils.py:19-110）（:1274-1284）
  3. 候補 (年, 月, 日) の None 以外が全部一致する行を当たりにする

**`parse_date_with_separators` の規則**（date_utils.py:268-338）
- NFKC → 先頭の漢字・かな元号（昭和/昭/しょうわ/ショウワ、平成/平/へいせい/ヘイセイ、令和/令/れいわ/レイワ）を S/H/R に → 大文字化 → 「年」「月」「日」を「.」に → `. / - 空白` で分割
- 先頭が S/H/R：元号年＋月＋日（3つ以上）、または元号年＋月（2つ）
- 数字3つ：年が 100 未満なら **30 未満は 2000年代、30 以上は 1900年代**（:321-322）
- 数字2つ：1つ目が 31 を超えれば「年・月」、それ以外は「月・日」（:325-334）
- 年の範囲：今年−100 ～ 今年+10（:279-280, :306, :323, :330）
- 実測例：`1989/2/3`→(1989,2,3)、`H1/2/3`→(1989,2,3)、`89/2/3`→(1989,2,3)、`29/2/3`→(2029,2,3)、`30/2/3`→(1930,2,3)、`11/23`→(None,11,23)、`2.4`→(None,2,4)、`1990-05`→(1990,5,None)、`昭和63年12月31日`→(1988,12,31)

**`parse_fuzzy_date` の規則**（date_utils.py:19-265）
- 元号は **S・H・R だけ**（`ERA_OFFSETS = {'S':1926,'H':1989,'R':2019}` :9）。100歳以上（今年−100 未満）は出さない。未来は今年+10年まで出す。
- 元号付き：`S60` `昭和60` `昭.60` → 年だけ（:55-62）。`H1-2-03` `S.51.5.1` → 年月日（:65-75）
- 数字だけ（数字以外は捨てて連結 :81-82）から、次を全部出す
  - 年だけ：4桁＝西暦、2桁＝S/H/R の各年＋2000＋yy＋1900＋yy（:113-138）
  - 月日：全ての切れ目で（:141-156）
  - 年月：年が1桁（S/H/R 各年＋200y）、2桁（S/H/R 各年＋20yy＋19yy）、4桁（:159-206）
  - 年月日：同上。**年が「0」1桁なら 2000年**（:229-231）
- 実測例（2026年に実行。結果は実行年で変わる）

  - `00512` → 5月12日、2000年5月12日、S63/H30 の5月12日

  - `M45` → M は無視され「45」として扱われる（S45 等）。`T1` → 0件

### 5-7. 一文字違い検索

**判定 `check_fuzzy_match_with_substring`（:416-457）**
- 検索語が1文字以下：しない
- 検索語が5文字以上：セル全体と編集距離1か（部分一致は見ない）（:425-426）

### 5-9. 色（RGB）の扱い（:744-888）

3. `#FFFFFF` `#000000` `#FEFEFE` などは無視（:804）

**B. 文字からの自動判定**（A で色が無い行だけ。全列の文字をつないで判定 :855-888）

## 11. 気づいた問題点・危険な所（直していない。指摘だけ）

### 重大
1. **API キーがソースに直書き**（customer_app.py:50 `DEFAULT_API_KEY`）。exe にも入る。ダイアログで先頭20文字を表示（:1797）、レジストリにも平文保存（:1613）。キーとして有効かは**未確認**だが、形式は Anthropic（Claude API）の API キーそのもの。使われるのは「フリガナ自動入力」だけ。→ 2026-11-10、本人の判断で**キー入りのまま非公開リポジトリに保存**した（本人の見立て：Windsurf の頃に入れた前払い分だけのキー。どこで使ったかは覚えていない）。キーの無効化・課金設定の確認は Claude Console（platform.claude.com の Settings → API keys / Billing）で本人が行う。
2. **フリガナ自動入力が元の Excel の数式を消す**：`openpyxl.load_workbook(…, data_only=True)` で開いて `wb.save()` で上書き（customer_app.py:1958, :1986）。data_only で開くと数式は値に置き換わり、そのまま保存すると数式が無くなる（実測：数式 `=ROW()-1` のセルが保存後 None）。**会員ID が数式**だとコード自身が書いている（:716, :738）ので、会員IDの数式が消える可能性が高い。保存前の複製（バックアップ）も取らない。.xlsm のマクロが保たれるかも未確認（`keep_vba` 指定なし）。
3. **pandas 3 だと読込失敗**（§2）。requirements で pandas<3 に固定しないと、入れ直した時に動かなくなる。
4. フリガナ生成の失敗を握りつぶす：バッチの API エラーは `except Exception:` で既存値に置き換えて続行（furigana_helper.py:125-129）。最後は「完了」と出て、件数も実際に変わった件数ではない（customer_app.py:1972-1974）。

### 検索の食い違い・誤り
5. `OR` `AND` `&` が区切りにならない（§5-1）。テスト（test_regression / test_and_or_search / test_results.txt）は区切り扱いで「合格」しており、本体とずれている。
6. 生年月日の文字が、全列検索では照合されず、「生年月日」列指定（誕生日ボタン）では照合される（§5-5、実測：`123` で 11/23 生まれが誕生日ボタンの時だけ出る）。
7. 「元年」を読めない（`平成元年1月8日` → 1月8日の全員）。M（明治）・T（大正）の元号は Excel 読込でも読めない（`T5.1.1`→読めず、実測）。parse_excel_date は M/T を想定した分岐（date_utils.py:491）を持つが `ERA_OFFSETS` に M/T が無い。

9. 100歳除外が「実行した年」基準。年が変わると検索結果が変わる（例：2026年は 1926年以降だけ）。未来は+10年まで候補に入る（例 `123` → R12＝2030年3月）。
