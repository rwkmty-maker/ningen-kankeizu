## A：本人の意図に反する、確実な不具合

### A1. フリガナ自動入力が、元の Excel の数式を消す（バックアップも取らない）【高】
- **何が起きるか**：「フリガナ自動入力」を実行すると、元の Excel を `data_only=True`（数式ではなく、保存済みの計算結果を読む指定）で開き、そのまま同じファイルに上書き保存する。数式のセルは値だけになる。会員ID が数式なら、それ以降は自動で番号が振られなくなる。Excel が一度も計算結果を保存していないセル（Excel 以外で作ったファイルなど）は空になる。保存の前に複製を取らない。
- **根拠**：customer_app.py:1958 `openpyxl.load_workbook(self.last_loaded_path, data_only=True)`、:1986 `wb.save(self.last_loaded_path)`。会員ID が数式であることはコード自身が書いている（:716, :721, :738 のコメント「数式の計算結果」）。数式が消えることは SPEC §11-2 が実測している（`=ROW()-1` が保存後 None）。.xlsm のマクロが残るか（`keep_vba` の指定なし）は未確認。
- **意図の洞察**：作った時の意図は「手で打つ手間を省き、結果を名簿そのものに残す」こと（:1953 のコメント「openpyxlで既存ファイルを直接更新」）。`data_only=True` は、読込（:721）で「会員IDの計算結果を読む」ために付けた指定を、書き込みにもそのまま写したものと見られる（推定。根拠：同じ書き方で、:1958 の前後に、書き込みのためにこの指定を選んだという説明が無い）。数式を消すつもりは無かったはず。
- **直すなら（案）**：書き込みは `data_only=False` で開いたブックに対して行う（フリガナのセルだけを書き換え、他のセルは触らない）。保存の前に、日時つきの複製を同じフォルダに作る。.xlsm なら `keep_vba=True` を付ける。直した後は、数式・書式・マクロ入りの架空ファイルで「保存前と後でフリガナ以外の全セルが同じ」ことを確かめるテストを作る。

### A2. フリガナ生成の失敗を握りつぶし、「完了」と出す。件数も実際と違う【高】
- **何が起きるか**：50件ずつの API 呼び出しのどれかが失敗しても（通信切れ・上限・課金切れなど）、その50件は「今のフリガナのまま」として続け、最後に「フリガナの自動入力が完了しました」と出す。「処理件数」は、名前が結果の辞書に入っていた行の数で、変えなかった行（スキップ・失敗）も数える。利用者は、どこが失敗したのか分からない。
- **根拠**：furigana_helper.py:125-129（`except Exception:` で既存の値を入れて続ける）、customer_app.py:1968-1974（`updated_count` は `name in results` の行を全部数える）、:1995-1998（完了の表示）。
- **意図の洞察**：「途中で止まると、それまでの課金が無駄になる」のを避けたかったと見られる（推定（根拠なし））。ただ本人の開発ルールは「エラーの握りつぶしで不具合を隠さない」。
- **直すなら（案）**：失敗したバッチは名前ごと記録し、最後に「成功 N件／変更なし M件／失敗 K件（失敗の理由）」を出す。失敗した人は書き込まない。書き込み済みの分を残すか全部取りやめるかは本人に決めてもらう。

### A3. pandas 3 だと、会員ID が整数だけの Excel が読めない【高（環境しだい）】
- **何が起きるか**：pandas を入れ直して 3 系になると、会員ID 列が全部整数（空欄なし）の Excel で「読込エラー」になる。
- **根拠**：customer_app.py:714 `pd.read_excel(path)`（型の指定なし）、:828 `df.at[idx, '会員ID'] = member_id`（文字を整数の列に入れる）。**実測**：pandas 3.1.1 で `Invalid value '1' for dtype 'int64'`、2.3.3 では警告だけで読めた（架空データ kaku3.xlsx。SPEC §2 と同じ結果）。会員ID 列に空欄が1つでもあると列は小数型になり、pandas 3 でも読めた（実測、kaku.xlsx）。
- **意図の洞察**：旧版は `dtype=object`（型を決めずにそのまま読む）だった（customer_app_v45_backup.py:196）。現行は :712 のコメント「数値データを保持したまま読み込み（dtype指定なし）」で、わざと外している。なぜ外したかは書かれていない（下の C6）。
- **直すなら（案）**：会員ID を入れる前に、その列を文字の列にしてから入れる（全部の列を文字にするのは :902-906 で後からやっているので、順番を入れ替えるだけで済む）。あわせて requirements で pandas の版を固定する。

### A4. 全列検索では、5文字以上の語の一文字違いが一度も当たらない【中】
- **何が起きるか**：検索対象の列を選んでいない（ふつうの使い方）と、5文字以上の語（フルネーム、電話番号の全桁など）の一文字違いが働かない。列を選ぶと働く。
- **根拠**：customer_app.py:424-426（5文字以上は部分を見ずに `check_fuzzy_match(query, target)`＝セル全体と比べる）、:484-486（列の指定が無い時は、全列をつないだ1本の文字 `search_index` を「1つのセル」として扱う）。行全体の文字と5文字の語が一文字違いになることは、まず無い。
  - **実測**（架空A のフリガナ `ｶｸｳｲﾁ`、電話 `090-0000-0001`）
    - `カクウイチX`（6文字）：全列 → 0件／フリガナ列を指定 → 架空A が一文字違いで出る
    - `090-0000-0002`：全列 → 0件／「電話番号」ボタンの列 → 架空A が出る
    - `カクウX`（4文字）：全列でも当たる（4文字以下は部分を見るため）
- **意図の洞察**：コメントは「5文字以上の場合は部分文字列チェックをスキップ（負荷軽減）」（:424）。作った時は「1つのセルと比べる」つもりで書かれ、後から `search_index`（全列をつないだ文字）でも同じ関数を使うようになって、意図しない形になったと見られる（推定。根拠：:428 のコメント「電話番号列または住所列」は列単位で考えている）。電話番号の打ち間違いを拾いたいのは本人の要求そのもの（test_and_or_search.py の「出禁 070」の例）なので、意図に反すると判断した。
- **直すなら（案）**：全列の時も、`search_index` 1本ではなく元の列ごとに比べる（5文字以上は「セル全体と編集距離1」の考え方のまま。列ごとなので重くならない）。速さが気になるなら、セルごとの正規化済みの文字を読込時に作っておく。

### A5. 一文字違いで全員が出ると、全員が「通常の一致」の見た目になる【中】
- **何が起きるか**：結果の件数が全件と同じになると、表示の時に全員を通常の一致として扱う。一文字違いだけで出た行にも、斜体・下線が付かない。利用者は「全員がこの語を含む」と読み違える。行IDも `fuzzy_…` にならない。
- **根拠**：customer_app.py:1460-1462（`len(self.current_indices) == len(self.df)` なら全部通常）。
  - **実測**：`架空Z`（ON）→ 9件中9件が一文字違いで出て、9件とも通常の見た目（行ID `0`〜`8`）。`カクウX`（全列、ON）も同じ。
- **意図の洞察**：この分岐の意図は「キーワード無しの全件表示（読込直後・リセット）では、余計な再計算をせず全部通常で出す」こと（:1459 のコメント「全件表示時は常に通常マッチとして扱う」、comprehensive_test.py:455-458「リセット時に表示様式がリセットされる」）。それを「件数が全件と同じ」で見分けたため、一文字違いで全件になった時まで巻き込んでいる。
- **直すなら（案）**：「全件表示かどうか」を件数で推し量らず、検索の時に「通常の一致の行」をそのまま覚えておき、表示ではそれを使う（A14・B12 も一緒に解決する）。

### A6. 登録名の前後に空白があると、関係図が「データなし」になる【中】
- **何が起きるか**：Excel の登録名の末尾（や先頭）に空白が入っている人をダブルクリックすると、関係図が出ず「データなし」になる。
- **根拠**：customer_app.py:1542-1544（`str(name).strip() != ''` で空かどうかだけ確かめ、渡すのは空白つきの `str(name)`）。graph_generator.py:113（図の点は `strip()` した名前で作る）、:155（中心の名前が図に無ければ「データなし」）。
  - **実測**：架空データ `架空D `（末尾に半角空白）→ `ValueError: データなし`。
- **意図の洞察**：図の側は、紹介者の欄と名前を合わせるために空白を落としている（:106, :113, :119）。画面の側で同じことをし忘れたと見られる。Excel への手入力では末尾の空白はよく入るので、実害が出やすい。

### A7. 生年月日が「年だけ」（例 1975）だと、明治38年（1905）5月28日と表示・検索される【中】
- **何が起きるか**：生年月日の欄に年だけ（数字4桁）が入っていると、Excel の日付の通し番号として読んで、1905年の日付にしてしまう。表示は `M38(1905)/05/28`。1975 では検索に当たらず、`1905` などで当たる。
- **根拠**：utils/date_utils.py:456-467（数字なら 1〜100000 を通し番号として読む。1900〜2100 の年もこの範囲に入る）。
  - **実測**：架空D の生年月日 `1975`（文字）→ `M38(1905)/05/28`、隠し列は (1905, 5, 28)。
- **意図の洞察**：通し番号の読み取りは、生年月日の列が「日付」ではなく「数値」の書式になっている Excel のため（:454 のコメント「シリアル値判定」）。年だけの入力は考えていなかったと見られる。年だけしか分からない客がいるかは**未確認**（影響の広さは実データしだい）。
- **直すなら（案）**：4桁で 1900〜今年の数は「年だけ」として扱う（隠し列は年だけ入れ、月日は空。表示は元の文字のまま）。通し番号として読むのは、それ以外の大きさの数だけにする。年だけの人をどう表示・検索したいかは本人に確認。

### A8. 「元年」が読めない（検索も、Excel の読込も）【中】
- **何が起きるか**：
  - 検索：`平成元年1月8日` と打つと「1月8日生まれの全員」になる（年が落ちる）。SPEC §5-6 の実測と同じ。

### A9. 日付の列（例 日付登録）の空欄が「NaT」と表示され、`at` `nat` で当たる【中】
- **何が起きるか**：生年月日以外の日付の列に空欄があると、画面に `NaT`（pandas の「日付なし」の印）と出る。全列の検索文字にも `NAT` が入るので、`at` や `nat` を含む語で、日付が空欄の人が全員当たる。
- **根拠**：customer_app.py:714（型の指定なしで読むと、日付の列は日付型になる）、:822（`fillna('')` は日付型の列の空欄を埋めない）、:904（`astype(str)` で `NaT` という文字になる）、:906（`'nan'` しか空にしない）。
  - **実測**（pandas 2.3.3）：日付登録が空の行 → 表示 `NaT`。`at`（OFF）→ 9件中8件（日付登録が空の8人）が当たる。
- **意図の洞察**：:906 で `'nan'` を空にしているので、「空欄は空欄に見せたい」のが意図。`NaT` は見落とされた。旧版は `dtype=object` なので起きにくかった（旧版での実測はしていない）。
- **直すなら（案）**：文字にした後に `NaT` も空にする、ではなく、文字にする前の段階で「欠けている値」をまとめて空にする（型によらず、pandas の欠損判定で埋める）。

### A10. 数値の列に空欄があると「1000001.0」と表示される【中】
- **何が起きるか**：郵便番号・電話番号などを数値で入れている列に空欄が1つでもあると、その列は小数型になり、表示が `1000001.0` のように `.0` 付きになる。検索の文字は `.` が消えて `10000010` になる（後ろに 0 が付く）。
- **根拠**：customer_app.py:714、:902-906。
  - **実測**：架空データの郵便番号 `1000001`（同じ列に空欄あり）→ 表示 `1000001.0`、search_index の末尾が `…10000010`。
- **意図の洞察**：会員ID だけは openpyxl で読み直して上書きしている（:716-742, :825-828）。これは会員ID でこの `.0` が出たのを直すためだった可能性が高い（推定。根拠：test_gui_comprehensive.py:238-296 が会員ID の「fillna 前後」「astype(str) 後」の型と値を1段ずつ表示して調べている。test_debug.py:4 の docstring「会員ID表示の問題を徹底調査」）。つまり**根本（型の指定を外したこと）ではなく、会員ID の列だけを個別に直した**形。

### A11. 表の先頭以外のシートを開いて保存すると、会員ID と色が別のシートから来る【中（条件つき）】
